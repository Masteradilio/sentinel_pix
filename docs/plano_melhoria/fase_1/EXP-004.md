## 1. Contexto

Na análise dos 23 FN da FASE 0 (ver `VALIDATION_REPORT.md §6.1`), identificamos um cluster problemático de fraudes chamadas **"formiguinhas"** — transações individualmente **inofensivas** (R$100-500) mas que, **em agregado**, representam **esvaziamento de conta** via múltiplas transferências em curta janela temporal.

### Evidência no sample 6k

Filtrando `fraudes_invisiveis_fn.csv` por `customer_id` com 2+ FN:

| customer_id | Tx 1 | Tx 2 | Valor agregado | Janela |
|---|---|---|---:|---|
| 6996881757 | R$425 | R$400 | **R$825** | ~1 min |
| 6865224191 (BLOQUEADO na 3ª) | R$997 | R$997 | **R$2.991** | ~6 min |

**Insight crítico:** o cliente `6865224191` fez **5 transações fraudulentas** em 7 minutos (13:39 a 14:10), das quais apenas a **3ª em diante** foi bloqueada via cascade `BURST_GTE3`. As duas primeiras passaram como BLOQUEAR via veto LGBM alto, mas em casos sem LGBM alto, essas "formiguinhas" **passariam invisíveis**.

### O que o sistema atual **não captura**
Cliente legítimo nunca faz 5 tx em 10 min. Sistema atual só ativa cascade BURST_GTE3 via IF≥99% E burst_30m_flag==1. Se fraudador é inteligente e faz 3 tx de R$400 em 15 min, cada uma com IF=0.75, LGBM=0.08 → TODAS PASSAM.

## 2. Hipótese

> Adicionar um padrão comportamental **`RATE_LIMIT_ANOMALO`** ao módulo BEH — que analisa a **janela temporal do próprio cliente** e dispara quando há **3+ transações em 30 minutos** OU **valor agregado > 2× média histórica do cliente em janela curta** — recupera 3 das fraudes "formiguinha" atualmente invisíveis, com FP esperado ≤ 2.

### Hipóteses Nulas

- **H0.1:** padrão recupera <2 fraudes (rejeita)
- **H0.2:** padrão gera >5 FP em sample de 6k (rejeita)
- **H0.3:** taxa de disparo > 3% do total (padrão generalista demais, rejeita)

---

## 3. Justificativa Técnica e de Negócio

### 3.1 Perfil de fraude "formiguinha"

Fraudadores sofisticados **conhecem thresholds**:
- Sabem que valores >R$1.000 ativam mais scrutiny
- Sabem que burst_30m dispara com ≥3 tx
- **Operam logo abaixo dos limites conhecidos**

Táticas típicas:
1. **Esvaziamento fracionado:** R$400 × 5 = R$2.000 sem disparar valor alto
2. **Janela longa fracionada:** 3 tx em 45 min (burla burst_30m)
3. **Beneficiários diferentes:** fraca correlação em módulos baseados em chave

### 3.2 Por que agregação por cliente é **essencial**

Análise atual é **stateless por transação**. Mas fraude é **padrão temporal**:

$$
P(\text{fraude} | \text{tx}_i) \neq P(\text{fraude} | \text{tx}_i, \text{tx}_{i-1}, ..., \text{tx}_{i-k})
$$

O sinal está no **histórico recente do cliente**, não na tx isolada.

### 3.3 Benchmark externo

Bancos brasileiros de ponta (Nubank, Itaú) usam rate limiting **como primeira linha de defesa PIX**. É feature obrigatória.

### 4.3 Definição Formal do Padrão

```python
from datetime import timedelta
from dataclasses import dataclass

@dataclass
class CustomerRateWindow:
    """Janela rolante de transações de um cliente."""
    tx_count_30min: int
    tx_count_60min: int
    sum_values_30min: float
    sum_values_60min: float
    distinct_receivers_30min: int
    avg_historical_value: float  # calculado dos últimos 90 dias


def pattern_rate_limit_anomalo(
    tx: dict,
    window: CustomerRateWindow,
) -> PatternResult:
    """
    Detecta padrão de rate limiting anômalo ("fraude formiguinha").

    Triggers (pelo menos UM dos abaixo):
      T1 — BURST_MODERADO: 3+ tx em 30min E sum >= R$500
      T2 — BURST_AMPLO:    4+ tx em 60min E sum >= R$1000
      T3 — VALOR_ANOMALO:  sum_30min >= 3× avg_historical_value
      T4 — DIVERSIDADE:    3+ beneficiários distintos em 30min

    Score:
      T1 ou T2  → 45 (MODERADO)
      T3        → 55 (MODERADO_ALTO)
      T4        → 60 (ALTO)
      2+ triggers → +20 bônus (cap 80)
    """
    triggers = []
    score = 0

    # T1: Burst moderado em 30min
    if window.tx_count_30min >= 3 and window.sum_values_30min >= 500:
        triggers.append("BURST_MODERADO_30M")
        score = max(score, 45)

    # T2: Burst amplo em 60min (pega fraudadores que burlam burst_30m)
    if window.tx_count_60min >= 4 and window.sum_values_60min >= 1000:
        triggers.append("BURST_AMPLO_60M")
        score = max(score, 45)

    # T3: Valor agregado 3x acima da média histórica
    if (
        window.avg_historical_value > 0
        and window.sum_values_30min >= 3 * window.avg_historical_value
        and window.sum_values_30min >= 300  # piso mínimo
    ):
        triggers.append("VALOR_AGREGADO_ANOMALO")
        score = max(score, 55)

    # T4: Múltiplos beneficiários em curta janela
    if window.distinct_receivers_30min >= 3:
        triggers.append("MULTI_RECEIVERS_30M")
        score = max(score, 60)

    # Bônus de convergência: 2+ triggers simultâneos = sinal forte
    if len(triggers) >= 2:
        score = min(80, score + 20)

    if triggers:
        return PatternResult(
            name="RATE_LIMIT_ANOMALO",
            triggered=True,
            score=score,
            severity=_severity_from_score(score),
            sub_patterns=triggers,
            explanation=(
                f"Rate limiting anômalo: {len(triggers)} trigger(s) "
                f"[{', '.join(triggers)}] — "
                f"tx_30m={window.tx_count_30min}, "
                f"sum_30m=R${window.sum_values_30min:,.2f}"
            )
        )
    return PatternResult(triggered=False)

5. Arquitetura de Implementação
5.1 Desafio: cálculo eficiente de janela rolante
Pipeline atual processa tx individualmente em workers paralelos. Rate limiting requer estado por cliente. Opções:

Opção A — Precompute por janela (recomendado) ⭐
python


# Em preprocessing, antes de paralelizar:
df_sorted = df.sort_values(['customer_id', 'event_datetime'])
df_with_windows = compute_rolling_windows(df_sorted, windows=['30min', '60min'])
# df_with_windows tem colunas: tx_count_30m, sum_30m, etc.
# Agora cada worker pode processar tx standalone.
Vantagem: mantém paralelismo, zero overhead em runtime. Desvantagem: precompute pesado em dataset grande (~2min em 100k tx).

Opção B — Cache Redis com TTL (produção futura)
Manter janela em Redis com TTL de 60min. Pipeline consulta por tx.

Vantagem: funciona em streaming real. Desvantagem: complexidade operacional pra FASE 1.

Decisão: Opção A pra FASE 1. Registrar Opção B como débito técnico pra FASE 2.

5.2 Cálculo de avg_historical_value
Média dos últimos 90 dias excluindo a janela de análise atual (evita data leakage temporal):

python


def compute_historical_avg(
    customer_id: str,
    current_tx_datetime: datetime,
    all_txs: pd.DataFrame,
    lookback_days: int = 90,
    exclusion_window_minutes: int = 60,
) -> float:
    """Média histórica, excluindo janela recente para evitar contaminação."""
    cutoff_recent = current_tx_datetime - timedelta(minutes=exclusion_window_minutes)
    cutoff_old = current_tx_datetime - timedelta(days=lookback_days)

    mask = (
        (all_txs['customer_id'] == customer_id)
        & (all_txs['event_datetime'] < cutoff_recent)
        & (all_txs['event_datetime'] >= cutoff_old)
    )
    historical = all_txs.loc[mask, 'vl_pix']

    return historical.mean() if len(historical) >= 3 else 0.0

6. Requisitos (EARS)
REQ-001 (ubiquitous): O padrão RATE_LIMIT_ANOMALO deve estar implementado no módulo BEH com versionamento (BEH v3.2).
REQ-002 (event-driven): Quando o pipeline recebe um dataset, o preprocessing deve computar janelas rolantes por customer_id antes de paralelizar.
REQ-003 (event-driven): Quando pelo menos um dos triggers (T1-T4) for satisfeito, o padrão deve adicionar score ao beh_score agregado.
REQ-004 (state-driven): Enquanto o cliente tiver menos de 3 tx históricas, o trigger T3 (valor anômalo) deve ser desativado para aquele cliente.
REQ-005 (unwanted): Se a taxa de disparo do padrão exceder 3% das transações, gerar warning.
REQ-006 (ubiquitous): O padrão deve ser controlado por flag rate_limit_pattern_enabled em config.
REQ-007 (event-driven): Quando múltiplos triggers disparam na mesma tx, o score recebe bônus de convergência (+20, cap 80).
