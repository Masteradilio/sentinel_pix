### Implicação

O `EXP-003` deixa de ser "recuperar 3/3 fraudes do cluster" e passa a ser:

> **Recuperar o caso residual remanescente e possíveis FNs similares no baseline atual, sem reabrir os FPs que o `EXP-002` acabou de reduzir.**

### Consequência de design

O spec original também assumia uma mecânica de score do `SE` que não bate exatamente com o runtime atual. Hoje:
- o `SE` agrega risco por **severidade de padrão**, não por um `score=55` contínuo como no pseudo-código
- portanto, apenas "criar um novo padrão SE" não garante sozinho a conversão `FN -> TP`

Por isso, a versão operacional deste experimento passa a ser:

1. adicionar um novo padrão `SE` para o cluster residual
2. expor esse padrão de forma auditável no output
3. testar uma **regra cirúrgica de confirmação no engine** baseada nesse padrão, respeitando o guard rail do `EXP-002`

Essa é a única forma de manter aderência ao objetivo de redução de `FN` no runtime real atual.

## 1. Contexto

Na validação da FASE 0 (ver `VALIDATION_REPORT.md §6.1 Padrão B`), **3 fraudes de alto valor escaparam** formando um cluster específico: perfis vulneráveis (idosos ≥60 ou jovens ≤25) com valores moderados-altos (R$1.500-10.000), onde **nenhum módulo disparou com força suficiente**.

### Fraudes perdidas

|---|---:|---:|---:|---:|---:|---:|---:|
| 33578893153 | **R$10.000** | 60 | 0.08 | 0.98 | 40 | 15 | 68.16 |

**Custo direto:** R$21.630 em fraudes não detectadas apenas nesse cluster.

### Por que escaparam?

- **LGBM baixo-moderado** (0.08-0.33): não cruza threshold interno (0.40)
- **IF alto** (>0.92): sinaliza anomalia mas sozinho não basta
- **SE ausente ou fraco** (0-40): nenhum padrão capturou esse perfil
- **BEH ausente ou fraco** (0-15)
- **Score final** 66-71: abaixo do threshold de CONFIRMAR (77)

O cluster é **perfeitamente detectável** com um padrão SE específico.

## 2. Hipótese

> Adicionar um novo padrão `IDOSO_JOVEM_VALOR_MODERADO` ao módulo Social Engineering — que dispara quando idade ∈ [≥60 OR ≤25] **E** valor ∈ [R$1.500, R$15.000] **E** conta relativamente nova (<24 meses) **E** IF≥0.90 — recupera 3/3 fraudes desse cluster com FP esperado ≤ 2.

### Hipóteses Nulas (H0)

- H0.1: Padrão recupera <2 das 3 fraudes (rejeita)
- H0.2: Padrão gera >5 FP (rejeita)

## 3. Justificativa de Domínio

### Perfis vulneráveis em fraude PIX

Literatura e dados BRB confirmam que **idosos (>60) e jovens (<25)** são estatisticamente mais vulneráveis a:
- Golpe do falso parente
- Golpe do falso suporte técnico
- Engenharia social via WhatsApp/telefone

Fraudadores frequentemente induzem vítimas a fazer **1-3 transferências de valor moderado-alto** (R$1k-R$15k) — valor suficiente para compensar o "esforço" mas abaixo dos thresholds mais agressivos.

### Por que combinar com IF≥0.90?

Isolation Forest detecta **anomalias comportamentais**: cliente que nunca fez tx desse tamanho, horário incomum, beneficiário novo, etc. IF alto + perfil vulnerável + valor moderado = **assinatura clássica de fraude social**.

### Por que conta <24 meses?

Clientes novos ainda não têm histórico comportamental rico. Fraudadores frequentemente abrem contas-laranja recentes para receber.

### 4.3 Definição Formal do Padrão

```python
def pattern_idoso_jovem_valor_moderado(tx: dict) -> PatternResult:
    """
    Detecta fraude social em perfis vulneráveis com valor moderado.

    Trigger (todos obrigatórios):
      - idade <= 25 OR idade >= 60
      - R$1.500 <= vl_pix <= R$15.000
      - qt_tempo_relacionamento_mes < 24
      - if_percentile >= 0.90

    Score: 55 (MODERADO-ALTO — contribui para CONFIRMAR via score_final)
    """
    idade = tx.get("nr_idade", 30)
    valor = tx.get("vl_pix", 0)
    relacionamento = tx.get("qt_tempo_relacionamento_mes", 999)
    if_pct = tx.get("if_percentile", 0)

    is_vulneravel = (idade <= 25) or (idade >= 60)
    is_valor_moderado = 1500 <= valor <= 15000
    is_conta_nova = relacionamento < 24
    is_anomalo = if_pct >= 0.90

    if all([is_vulneravel, is_valor_moderado, is_conta_nova, is_anomalo]):
        return PatternResult(
            name="IDOSO_JOVEM_VALOR_MODERADO",
            triggered=True,
            score=55,
            severity="MODERADO_ALTO",
            explanation=(
                f"Perfil vulnerável (idade={idade}) + valor moderado "
                f"(R${valor:,.0f}) + conta nova ({relacionamento}m) + "
                f"anomalia IF ({if_pct:.1%})"
            )
        )
    return PatternResult(triggered=False)

9. Considerações Éticas (Artigo IX da Constituição)
Auditoria de Bias Obrigatória
O padrão explicitamente usa idade como feature — atributo protegido indiretamente (correlação com outros protegidos possível).

Mitigações obrigatórias:

 Padrão só contribui para o score, não bloqueia sozinho (CONFIRMAR requer +outros sinais)
 Score 55 é moderado, não decisivo
 Análise trimestral de bias: precision/recall por faixa etária
 Explicação ao cliente bloqueado deve ser clara (não mencionar idade como único fator)
 Padrão exige IF≥0.90 (anomalia comportamental), evitando discriminação por idade sozinha
Contrapesos
Padrão captura vítimas vulneráveis — cumpre dever de proteção
Atua em conjunto com anomalia comportamental (IF) — não é "só idade"
Leva a CONFIRMAR (2FA), não BLOQUEAR — fricção recuperável
