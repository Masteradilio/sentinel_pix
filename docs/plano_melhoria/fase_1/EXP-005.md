## 1. Contexto

O LightGBM atual do pipeline (Engine v3.0.5) foi treinado otimizando **F1-score padrão** — que trata FP e FN com pesos equivalentes. Porém, a `CONSTITUTION.md §2.1` estabelece que **antifraude PIX tem assimetria estrutural**: custo de FN ≫ custo de FP.

Análise dos 23 FN (`fraudes_invisiveis_fn.csv`) revela **7 casos** com `lgbm_raw` entre **0.20 e 0.48** — ou seja, o modelo "**quase acertou**" mas ficou abaixo do threshold interno (0.40):

### Por que não só reduzir o threshold do LGBM?

Reduzir o threshold (ex: 0.40 → 0.25) é **solução paliativa**. O EXP-005 vai **um nível mais profundo**: retreinar o modelo com função de perda **consciente da assimetria**, gerando uma curva precision/recall melhor **em toda a faixa operacional**.

## 2. Hipótese

> Retreinar o LightGBM com **função de perda assimétrica** (via `scale_pos_weight`, `focal loss` ou `class_weight customizado`) — otimizando **Recall@Precision≥0.90** em vez de F1 — recupera **2 fraudes** atualmente FN (lgbm_raw entre 0.20-0.40) sem degradar F1 global do pipeline.

### Hipóteses Nulas

- **H0.1:** recall@precision=0.90 não melhora ≥2pp (rejeita)
- **H0.2:** precision do modelo cai abaixo de 85% (rejeita — perda operacional inaceitável)
- **H0.3:** pipeline full tem F1 < baseline - 0.005 (rejeita — degradação)

## 3. Justificativa Técnica

### 3.1 Função de perda atual (assumida)

Binary log-loss padrão:

$$
\mathcal{L}_{\text{log}} = -\frac{1}{N} \sum_{i=1}^{N} \left[ y_i \log(\hat{p}_i) + (1 - y_i) \log(1 - \hat{p}_i) \right]
$$

Trata FP e FN **simetricamente**. Em datasets desbalanceados (0.35% de fraude), o modelo fica **viesado para a classe majoritária** (legítima) mesmo com class balancing básico.

3.3 Evidência de literatura
Lin et al. (2017) — "Focal Loss for Dense Object Detection": focal loss melhora recall em 2-4pp em datasets altamente desbalanceados.
Elkan (2001) — "The Foundations of Cost-Sensitive Learning": ajuste de scale_pos_weight = razão de custos é ótimo Bayesiano sob assimetria.
Fraud detection benchmark (Kaggle IEEE-CIS 2019): modelos com cost-sensitive loss tiveram AUC-PR 3-5% superior.
3.4 Por que não apenas SMOTE ou oversampling?
SMOTE gera fraudes sintéticas que não existem no mundo real. Em antifraude, fraudes reais têm assinaturas comportamentais específicas — sintéticas podem distorcer o modelo. scale_pos_weight e focal loss preservam os dados reais.

import numpy as np

def focal_loss_lgbm(alpha: float = 0.75, gamma: float = 2.0):
    """Gera callbacks de focal loss para LightGBM custom objective."""

    def objective(y_true: np.ndarray, y_pred: np.ndarray):
        """Retorna gradiente e hessiana."""
        p = 1.0 / (1.0 + np.exp(-y_pred))  # sigmoid
        p = np.clip(p, 1e-7, 1 - 1e-7)

        # Focal weight
        pt = np.where(y_true == 1, p, 1 - p)
        alpha_t = np.where(y_true == 1, alpha, 1 - alpha)
        focal_w = alpha_t * (1 - pt) ** gamma

        # Gradiente
        grad = focal_w * (p - y_true)
        # Hessiana (aproximada)
        hess = focal_w * p * (1 - p) * (1 + gamma * (1 - pt))

Durante treino, early stopping baseado em recall@precision=0.90 na validação — não em F1:

python


def custom_eval(y_true, y_pred):
    thresholds = np.arange(0.01, 1.0, 0.01)
    best_recall = 0
    for t in thresholds:
        preds = (y_pred >= t).astype(int)
        tp = ((preds == 1) & (y_true == 1)).sum()
        fp = ((preds == 1) & (y_true == 0)).sum()
        fn = ((preds == 0) & (y_true == 1)).sum()
        if tp + fp == 0:
            continue
        precision = tp / (tp + fp)
        recall = tp / (tp + fn) if (tp + fn) > 0 else 0
        if precision >= 0.90 and recall > best_recall:
            best_recall = recall
    return "recall_at_p90", best_recall, True
