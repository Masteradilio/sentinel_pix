Limitações da agregação linear
Não captura interações não-lineares entre módulos
Exemplo: LGBM=0.3 + IF=0.9 pode ser MUITO mais preditivo que LGBM=0.5 + IF=0.5 (mesmo score linear)

Pesos fixos não são ótimos em todas as regiões do espaço
Quando LGBM é confiante, ele deveria ter mais peso. Quando incerto (score médio), SE/BEH deveriam dominar.

Calibração manual não escala
Adicionar um novo módulo requer recalibrar todos os pesos no braço.

2. Hipótese
Treinar um meta-learner (stacking) que recebe como input as saídas dos 4 módulos primários (LGBM, IF, SE, BEH) + features-chave de transação — e aprende a combinação ótima não-linear — produz pipeline com F1 ≥ 0.97 e Recall ≥ 99%, recuperando 2-3 fraudes FN adicionais que a agregação linear perde.

Hipóteses Nulas
H0.1: meta-learner não melhora F1 ≥ 0.005 sobre agregação linear (rejeita)
H0.2: meta-learner reduz explicabilidade (SHAP desestabilizado) (rejeita)
H0.3: meta-learner degrada em holdout temporal (rejeita — overfit)
3. Fundamentos Teóricos
3.1 Stacking (Stacked Generalization)
Técnica introduzida por Wolpert (1992) — treina modelo de nível 2 sobre previsões de modelos de nível 1:



Nível 1 (base learners):
  ├── LGBM     → p_lgbm
  ├── IF       → p_if
  ├── SE       → p_se
  └── BEH      → p_beh

Nível 2 (meta-learner):
  input:  [p_lgbm, p_if, p_se, p_beh, + features auxiliares]
  output: p_fraud_final
3.2 Por que LGBM/XGBoost como meta-learner?



Opção	Prós	Contras
LightGBM ⭐	Lida com não-linearidades, feature importance, rápido	Mesma família que base learner (risco de overfit no mesmo viés)
XGBoost	Diversidade algorítmica (boost diferente)	Levemente mais lento
Regressão Logística	Interpretável, calibrada naturalmente	Não captura não-linearidades
Rede Neural (MLP)	Máxima flexibilidade	Overkill para 4-10 features, difícil de explicar
Decisão: testar LightGBM (V1) e Regressão Logística (V2) como meta-learners. LR serve como sanity check: se ela ganha do LGBM, o problema é linear e não precisamos de stacking complexo.

3.3 Prevenção de overfitting
Problema crítico: se treinarmos o meta-learner com os mesmos dados usados para treinar os base learners, ele aprende memorização, não generalização.

Solução: Out-of-fold predictions (OOF):

python


from sklearn.model_selection import KFold

def generate_oof_predictions(base_model, X, y, n_splits=5):
    """Gera predições fora-da-fold para evitar leakage."""
    oof_preds = np.zeros(len(y))
    kf = KFold(n_splits=n_splits, shuffle=False)  # temporal-safe
    for fold_idx, (train_idx, val_idx) in enumerate(kf.split(X)):
        model = clone(base_model)
        model.fit(X.iloc[train_idx], y.iloc[train_idx])
        oof_preds[val_idx] = model.predict_proba(X.iloc[val_idx])[:, 1]
    return oof_preds

5.1 Novo módulo: MetaScorer
python


# backend/core/meta_scorer.py
import lightgbm as lgb
import numpy as np
from dataclasses import dataclass

@dataclass
class MetaScorerInput:
    """Input padronizado para o meta-learner."""
    p_lgbm: float
    p_if: float
    p_se: float
    p_beh: float
    vl_pix_log: float
    idade_bucket: int  # 0=jovem, 1=adulto, 2=idoso
    is_first_tx_trimestre: int
    first_receiver_flag: int
    pix_key_random_flag: int

    def to_array(self) -> np.ndarray:
        return np.array([
            self.p_lgbm, self.p_if, self.p_se, self.p_beh,
            self.vl_pix_log, self.idade_bucket,
            self.is_first_tx_trimestre,
            self.first_receiver_flag,
            self.pix_key_random_flag,
        ]).reshape(1, -1)


class MetaScorer:
    """Meta-learner que agrega sinais dos módulos base."""

    def __init__(self, model_path: str, version: str = "1.0"):
        self.model = lgb.Booster(model_file=model_path)
        self.version = version

    def score(self, inp: MetaScorerInput) -> float:
        """Retorna probabilidade final de fraude ∈ [0, 1]."""
        prob = self.model.predict(inp.to_array())[0]
        return float(prob)

    def score_with_contribution(self, inp: MetaScorerInput) -> dict:
        """Retorna score + SHAP contributions para explicabilidade."""
        prob = self.score(inp)
        shap_values = self.model.predict(
            inp.to_array(), pred_contrib=True
        )[0, :-1]  # último é bias
        feature_names = [
            "p_lgbm", "p_if", "p_se", "p_beh",
            "vl_pix_log", "idade_bucket", "is_first_tx",
            "first_receiver", "pix_key_random",
        ]
        return {
            "prob": prob,
            "contributions": dict(zip(feature_names, shap_values)),
        }

# backend/core/decision_engine.py
def decide(self, tx: dict, components: dict) -> Decision:
    if self.config.engine_mode == 'meta':
        # Novo caminho: meta-learner
        meta_input = self._build_meta_input(tx, components)
        prob_fraud = self.meta_scorer.score(meta_input)
        score_final = prob_fraud * 100  # compatibilidade com thresholds atuais
    else:
        # Caminho legado: agregação linear
        score_final = self._compute_linear_score(components)

    decision = self._apply_thresholds(score_final)
    decision = self._apply_vetos(decision, components)  # vetos permanecem
    return decision
5.3 Convivência com vetos
Decisão arquitetural importante: vetos (VETO BLOQUEAR, VETO CONFIRMAR) permanecem mesmo em modo meta. Por quê?

Vetos representam regras de negócio hard (compliance, limites regulatórios)
Meta-learner é probabilístico — vetos são determinísticos
Defesa em profundidade: se meta-learner falhar, vetos ainda protegem
